## 一、系統目的

本系統以「職位」為核心，先建立 VT 廠的組織、職位定義、編制人數與任職要求，再逐步加入現任者及潛在接班人資料。後續可將人員能力、語言能力與必要歷練，逐項對照職位要求，呈現落差並作為培訓計畫的依據。

產品名稱維持「VT 職位與人才管理系統」；第一階段的實際用途為主管對焦，但不以「主管對焦工具」作為對外顯示名稱。

第一階段先完成主管對焦所需的職位管理功能，不自行推測尚未提供的人員、接班人或職位資料。所有不確定內容保留「待確認／待訪談／建議新增／權責調整」標示。

- 系統名稱：VT 職位與人才管理系統。
- 組織名稱統一使用「秘書室」。
- 已加入「人員盤點」初稿檢視；目前只呈現原始盤點文件與待確認欄位，不進行量化評分或培訓管理。
- 網頁可查看組織圖、職位列表及職位明細。
- 網頁可編輯職位資料，修改結果保存於本機資料庫。
- 每份工作說明書需有唯一代碼，並以獨立主檔保存；系統可新增及編輯工作說明書主檔。
- 組織圖中的職位節點可選擇關聯工作說明書；多個職位配置可共同引用同一主檔，但各自保留單位、編制與人員資料。
- 每個職位可設定編制人數，並可登錄 0 至多位現任者；系統自動呈現現職人數及缺額。
- 同一職位定義可對應多個編制名額，例如同一種高專職位可有 2 名現任者。
- 預設為展示模式；組織新增、刪除、拖拉及調整從屬關係，必須進入「組織編輯模式」後才能操作。
- 未來正式上線後，只有 Admin 角色可進入組織編輯模式；本機第一版先保留相同的操作邊界，不開發完整帳號權限。
- 每個職位只保留一組確認狀態、確認人、確認日期及確認備註。
- 系統需提供待確認事項總覽；每個尚未完成主管確認的職位或人員只列一項，可直接進入對應明細。
- 職位明細可切換為 A4 列印版面，供列印或另存 PDF。
- 正式上線前只在 Ivy 的電腦執行，不對外部署。
- 主管於網頁確認及修改資料後，再由 Codex 依本機資料庫內容同步修改職位 Markdown 檔。
- 「VT 廠秘書室專員」無實際資料，第一階段不納入組織圖、職位列表及資料庫種子資料。

## 四、第一階段頁面

### 1. 總覽

- 顯示職位、編制、現職、缺額及確認進度摘要。
- 顯示編制人數、現職人數及缺額的整體摘要。
- 提供「待確認事項」清單，每個未完成主管確認的職位或人員只列一項。
- 點擊待確認事項後，直接開啟對應職位或人員明細。
- 總覽只統計有資料依據的內容；沒有資料時顯示「待確認」，不以 0 取代未知值。

### 2. 組織圖

- 以樹狀方式呈現廠主管、部門、單位及職位的從屬關係。
- 部門節點與職位節點採不同外觀。
- 可展開及收合組織分支。
- 點擊職位節點可進入職位明細。
- 預設展示模式不顯示移動、刪除等控制元件，也不接受拖拉。
- 進入「組織編輯模式」後，才可新增子部門、子單位或子職位。
- 組織編輯模式支援拖拉調整節點的上層歸屬；儲存前顯示原歸屬、新歸屬及確認訊息。
- 組織編輯模式不允許形成循環從屬，也不允許將根節點拖入下層。
- 未來上線時只有 Admin 可進入組織編輯模式。

### 3. 已建職位列表

- 顯示職位名稱、所屬部門／單位、職等、直接主管、編制人數、現職人數、缺額、現任者、資料狀態、版本及更新日期。
- 可依部門、單位、職等及資料狀態篩選。
- 可依職位名稱搜尋。
- 點擊資料列後進入與組織圖相同的職位明細頁。
- 尚未建立工作說明書的職位與已有初稿的職位需明確區分。

### 4. 職位明細與編輯

預計欄位區塊：

1. 職位基本資料：名稱、廠區、部門、單位、職等、直接主管、管理對象、代理人、編制人數、現職人數、缺額、資料狀態、版本、生效日及更新日期。
2. 職位目的／職位介紹。
3. 主要職責：代碼、內容及標註類型。
4. 決策與權限。
5. 績效衡量方向。
6. 關鍵能力。
7. 任職條件與必要歷練。
8. 語言要求：第一階段依現有資料，分別保留中文／國語、越文、英文要求、實際使用情境及待確認內容；完整標準化能力矩陣延後處理。
9. 現任者：由既有人員主檔工號帶入，可新增及移除多位現任者，顯示姓名、員工編號、到任日期（如有）及備註；不在職位頁重複維護姓名。
10. 潛在接班人：同樣由既有人員主檔工號帶入，可建立多筆待確認關係；第一階段不建立接班準備度或量化能力落差。
11. 訪談重點（底層保留，目前網頁與列印不顯示）。
12. 資料來源、機密等級及修訂資訊（底層保留，目前網頁與列印不顯示）。

編輯原則：

- 檢視模式與編輯模式分開，避免主管瀏覽時誤改。
- 儲存前檢查必填欄位；取消編輯時不覆寫原資料。
- 「待確認／待訪談／建議新增／權責調整」為結構化標註，不只是一段紅色文字，以利後續篩選與追蹤。
- 每個職位只保存一組確認狀態、確認人、確認日期及確認備註，不要求每個內容區塊重複確認。
- 職位整體狀態採「待建立 → 訪談前初稿 → 主管確認中 → 待修正 → 已確認 → 正式生效」。
- 現任者及潛在接班人尚無可靠資料時顯示「待確認」，不得自行補入姓名。
- 後續若加入人員資料，職位要求與人員實際能力分開保存，不以修改職位資料的方式改寫人員能力。

### 5. PDF／列印畫面

- 由職位明細頁進入列印預覽。
- A4 直式、Noto Sans TC、上下邊距 1.5 cm。
- 標題 15 pt、內文 10 pt、表格 9 pt。
- 使用深藍標題與表格交錯底色。
- 待確認類標註於列印版顯示紅字。
- 頁首顯示職位名稱、文件版本、文件狀態及更新日期；畫面不顯示「機密／人事機密」標籤。
- 不顯示「主管對焦版／尚未正式生效」及「職位確認進度」元件。
- 「編制與現任者」只顯示於網頁，不納入列印／PDF。
- 不顯示導覽列、編輯按鈕、拖拉控制及其他操作元件。
- 第一階段採瀏覽器列印／另存 PDF；若日後需要固定檔名、批次輸出或正式版號，再增加系統產檔功能。

## 五、本機資料保存與同步原則

### 本機資料庫

- 第一階段使用本機 SQLite 資料庫，不使用瀏覽器暫存作為正式資料來源。
- 網頁重新整理或關閉後，已儲存內容仍需保留。
- 資料庫檔、備份檔及人員資料不得提交至公開儲存庫或對外傳送。
- 正式部署時再評估將 SQLite 結構遷移至雲端資料庫，並補上登入、權限及稽核機制。

### Markdown 同步

- 第一階段的正式編輯來源為本機資料庫；現有 Markdown 作為初始匯入來源與主管確認後的文件輸出。
- 網頁儲存後先不直接覆寫 Markdown，避免格式或人工註記意外遺失。
- 只有在 Ivy 明確下達同步指令後，Codex 才進行 DB 與 Markdown 的差異比對及文件更新。
- 每次同步前由 Codex 比較資料庫與 Markdown 差異，列出修改項目後再更新文件。
- 同步時保留 YAML 基本資料、章節結構、標註語法與來源資訊。
- Markdown 標註統一使用 `🔴 **標籤｜內容**`，不得使用 HTML 顏色語法。
- 若資料庫與 Markdown 同一欄位均有後續人工修改，以差異清單標示衝突，不自動選擇其中一版。
